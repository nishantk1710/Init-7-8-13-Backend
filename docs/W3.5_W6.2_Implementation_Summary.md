## Part 1 — W6.2: Reservation data source

### Objective
Give the I13 ledger's Reservation leg (`Reservation → PR → PO → GR → GI`) a
real-data option, since live SAP `ReservationItemSet` (CPI/OData) returns 0
rows — without fabricating disconnected test data.

### Key finding
The live **CPI/OData** RESB feed is genuinely empty (0 rows) — but the
**Postgres raw extract** (`raw_resb`, loaded separately from `RESB.XLSX`) was
NOT empty: 105,848 real rows, 1,274 referencing a real PR, 472 of those
joining cleanly to real `raw_eban` rows.

### Files added
| File | Purpose |
|---|---|
| `app/integrations/sap/postgres_reservation.py` | `PostgresReservationProvider` — reads real `raw_resb`, normalizes to the existing `ReservationItemSet` row shape (`Rsnum, Rspos, Matnr, Werks, Bdter, Bdmng, Banfn, Bnfpo, Aufnr, ...`) |
| `tests/i13/test_reservation_postgres.py` | 4 DB-gated tests |

### Files modified
| File | Change |
|---|---|
| `app/integrations/sap/gateway.py` | `get_reservations()` switches mock ↔ Postgres via config; lazy — never touches DB unless selected |
| `app/core/config.py` | added `i13_reservation_source: str = "mock"` |
| `app/shared/material_scope/policy.py` / `__init__.py` | added `build_scope_index()` (consolidates OAR-index logic previously duplicated in `exceptions.py`) |
| `app/initiatives/i13/exceptions.py` | now calls the shared `build_scope_index` |
| `app/api/i13/ledger.py` | `/api/i13/ledger` and `/ledger/{id}` now default to **OAR-scope only** (`include_out_of_scope=true` to see everything) — this was a real gap: every other W6.x endpoint already applied W2.4 OAR scope; the ledger endpoint didn't |
| `.env.example` | documented `I13_RESERVATION_SOURCE` |

### Formula / logic
No new business formula — this is a data-source swap. Reservation → PR join
is exact-match only on `Banfn`+`Bnfpo` (no fuzzy matching, per spec).

### Config switch
```
I13_RESERVATION_SOURCE=mock       # default — synthetic CSV, self-consistent PR/PO/GR/GI chain
I13_RESERVATION_SOURCE=postgres   # real raw_resb rows (requires DATABASE_URL)
```
Default stays `mock` because PR/PO/GR/GI are still on synthetic CSV
(`LiveSapGateway`) — a Postgres-sourced reservation's real `Banfn` won't
match anything in the synthetic PR set, so it would just show as
`UNMATCHED`. This was a deliberate, discussed tradeoff, not an oversight.

### Real-data proof (verified against Postgres directly, not fabricated)
```
Reservation 1841579/1 (material 8000000141, plant 1300, qty 1)
  → PR 2000028108/10        (raw_eban)
  → PO 4500001595/10        (raw_eban.purchase_order)
  → GR qty 1, 2025-11-07    (raw_ekbe, po_history_category=E)
  → GI: none yet in this extract (honest gap, not fabricated)

Reservation 1920747 (no PR — direct-consumption reservation)
  → GI movements exist directly (raw_mseg, type 201, 2025-08-08),
    quantities match raw_resb.quantity_withdrawn exactly
```

## Part 2 — W3.5: Statistics-independent aging

### Objective
Compute movement/aging metrics (last movement, last issue, trailing-12-month

### Files modified
| File | Change |
|---|---|

### SAP → Postgres field mapping (discovered, not assumed)
| SAP concept | Postgres column |
|---|---|
| MATNR | `raw_mseg.material` / `raw_mard.material` |
| WERKS | `raw_mseg.plant` / `raw_mard.plant` |
| MBLNR+MJAHR | `material_document` + `material_doc_year` (mseg↔mkpf join key) |
| BWART | `raw_mseg.movement_type` |
| MENGE | `raw_mseg.quantity` |
| BUDAT | `raw_mkpf.posting_date` (0 mismatches vs. `raw_mseg.posting_date` across 232,273 joined rows — joined to MKPF anyway, per the header being the SAP-correct source) |
| LABST | `raw_mard.unrestricted` |

### Formulas implemented
```
last_movement_date        = MAX(posting_date) over ANY qualifying movement
days_since_last_movement  = as_of − last_movement_date

last_issue_date            = MAX(posting_date) over goods-ISSUE movements only
days_since_last_issue      = as_of − last_issue_date
                              (kept independent of last_movement_date —
                               a pure receipt does not reset this)

consumption_count_12m,
consumption_qty_12m       = reversal-netted count/sum of issue movements
                             in the rolling 12-calendar-month window ending as_of

aging_band                = classify(days_since_last_issue, thresholds)
                             FAST 0–365 / SLOW 366–730 / NON_MOVING >730
                             (classified on LAST ISSUE, not last movement —
                              see the open question below)

inventory_turns           = consumption_qty_12m / current_stock
                             None + reason "INSUFFICIENT_HISTORY" if stock
                             is unknown or zero (current-stock PROXY, not a
                             true trailing-average — raw_mard has no history)
```

### Consumption / receipt / reversal rule used
Reused **unchanged** from the existing `app/initiatives/i13/movements.py`
(not reinvented):
```
RECEIPT_TYPES = {"101"}
ISSUE_TYPES   = {"201", "261"}
REVERSAL_OF   = {"102": "101", "202": "201", "262": "261"}
```
Verified against real data: 2,365/2,473 real `102` rows carry a
`reference_document` resolving to a real `101` row with matching quantity.

### Real output, cross-checked against the underlying rows
```
GET /api/i13/materials/5000017191/plants/1300/movement-metrics
{
  "last_movement_date": "2026-08-13", "days_since_last_movement": 33,
  "last_issue_date": "2026-07-30",   "days_since_last_issue": 47,
  "consumption_count_12m": 302,       "consumption_qty_12m": "638",
  "inventory_turns": "12.5098...",    "aging_band": "FAST"
}
```
Manually confirmed: the 08-13 movement was type `311` (a storage-location
transfer — correctly excluded from `last_issue_date`); stock across 3
storage locations summed to 51; `638 ÷ 51 = 12.5098...` — matches exactly.

## Open business questions (raise with your lead / SAP-MM)

1. **Aging basis** — this module classifies on last *issue*; the pre-existing
   CSV-based `aging.py` (still used by `/summary`, `/watch`,
   `/reclassification`, `/exceptions`) classifies on last *movement* of any
   kind. Two definitions currently coexist — which is authoritative?
2. **Consumption movement-type allowlist** — only `201`/`261` count.
   Real data has `301`/`321` (transfers), `501` (GR w/o PO), `601` (sales
   issue), `641` (STO), `241` (asset issue), `541`/`543` (subcontracting),
   `701`/`702` (physical inventory) — none currently classified either way.
3. **Inventory-turns formula** — no VZI-approved formula exists; implemented
   as `consumption ÷ current stock` (a snapshot proxy, not a true average).
4. **Reversal-pair completeness** — only 3 pairs mapped; would need
   extending if #2 changes. Is there an authoritative SAP config table
   (e.g. OMBS) to use as source of truth instead of inferring from data?
5. **~53% of real GR (`101`) rows have a blank material** in the extract
   (issue rows are 0% blank) — known extraction gap or defect?
6. **Stock components for turns** — only `unrestricted` used, excluding
   QI/blocked/restricted stock (matches the pre-existing CSV-based
   convention). Correct per VZI's definition of "available inventory"?
7. **Material-number normalization** — no padding utility exists anywhere in
   the repo; Postgres materials are unpadded, other paths use 18-digit
   zero-padded MATNR. Needs a canonical format decision.
8. **"Never consumed" vs. "went dormant"** — both currently read as
   `NON_MOVING`. Worth a distinct `NO_HISTORY` state?
