## 1. What W7.4 must do

**Dev Plan W7.4:**
> Quantity-suggestion engine on a months-of-cover basis: trailing twelve-month consumption net of stock on hand and open POs; nudge against the configured cover ceiling; override justification.

**FRS FR-3:**
> Compute months of cover for the requested quantity from trailing twelve-month consumption at the plant, net of stock on hand and open POs. Suggest the quantity that covers the stated plan window; nudge down where the request exceeds the configured cover ceiling; nudge up where it falls short of the plan need. Cover ceiling, look-back window and minimum history are configuration. No suggestion where history is below the minimum.

Three further FRS constraints shape the design:

| Ref | Constraint |
| --- | --- |
| §6 (NFR) | Cover ceiling, look-back and minimum history are **configuration, not code** |
| §9 (Acceptance) | The assistant presents a suggestion **with reason** where history permits, and captures a justification where the requester keeps a different quantity |
| §8 (Savings) | Benefit is counted **only where the requester accepted the suggestion**, evidenced through the session link — so acceptance must be recorded, not just the suggestion |

## 2. What already exists — the reason this is a small package

Every input FR-3 needs is already computed by W6.3 and persisted in `i13_watch_metric_mart`:

| FR-3 input | Already available as |
| --- | --- |
| Trailing 12-month consumption rate | `average_monthly_consumption` |
| Stock on hand | `stock_on_hand` |
| Open purchase orders | `open_po_quantity` (ordered − received) |
| Months of cover | `months_of_cover`, `projected_months_of_cover` (already net of open POs) |
| History sufficiency | `consumption_count_12m` |

And the **consumer is already built**. W6.6 contains `QuantityDecisionRecord` and `detect_quantity_override()`, carrying this comment:

> *"`suggested_quantity` is `None` whenever no quantity-suggestion source is wired in (true for every caller today — the suggestion engine is W7.4)"*

So W7.4 is bounded on both sides: inputs exist, and the downstream exception path is waiting. **The new work is the calculation, two entities, four settings and an API surface** — not new data plumbing.

## 3. Critical sequencing insight

**W7.4 does not depend on W7.3 and can be built first.**

The Dev Plan lists W7.4's dependencies as W6.3 and W1.5 only — not W7.3. The one value W7.4 needs from the consumption plan is the **plan window in months**. If that is an explicit input parameter rather than a lookup, the engine is fully buildable and testable standalone, and wires to W7.3's `ConsumptionPlan` later without change.

This matters because W7.3 is the larger, slower package (chat flow, ChatSession, session issuance). Building W7.4 first de-risks the WS7 chain and gives W6.6 a working quantity-override path earlier.

```
W6.3 (built) ──▶ W7.4 (this plan) ──▶ W6.6 quantity-override (built, idle)
                      │
                      └── plan window as a parameter now,
                          supplied by W7.3's ConsumptionPlan later
```

## 4. The calculation, decomposed

Per `(material, plant)`, given a requested quantity and a plan window:

```
Inputs
  AMC   = average_monthly_consumption        (W6.3)
  SOH   = stock_on_hand                      (W6.3)
  OPO   = open_po_quantity                   (W6.3)
  HIST  = consumption_count_12m              (W6.3)
  W     = plan window in months              (W7.3, or parameter)
  Q_req = requested quantity                 (BAdI deep link)

Config
  CEILING = cover ceiling in months
  MIN_HIST = minimum history
```

**Step 1 — Minimum-history gate.**
If `AMC == 0` or `HIST < MIN_HIST` → **no suggestion**, reason `INSUFFICIENT_HISTORY`.
FRS §3.1 is explicit: *"No suggestion is made where there is no consumption history."* The engine must decline, never guess.

**Step 2 — Express the request as months of cover** (FR-3's first sentence):
`resulting_cover = (SOH + OPO + Q_req) / AMC`

**Step 3 — Plan need** (*"the quantity that covers the stated plan window"*):
```
plan_need = AMC × W
net_need  = max(0, plan_need − (SOH + OPO))
```

**Step 4 — Ceiling nudge** (*"nudge down where the request exceeds the configured cover ceiling"*):
```
ceiling_qty = max(0, (CEILING × AMC) − (SOH + OPO))
if Q_req > ceiling_qty  →  suggest ceiling_qty, direction DOWN, reason EXCEEDS_COVER_CEILING
```

**Step 5 — Shortfall nudge** (*"nudge up where it falls short of the plan need"*):
```
if Q_req < net_need  →  suggest net_need, direction UP, reason BELOW_PLAN_NEED
```

**Step 6 — Otherwise** → `direction NONE`, suggested = Q_req, reason `ALIGNED`.

### The conflict case that needs a ruling

If `net_need > ceiling_qty`, the stated plan window demands more than the cover ceiling permits. FR-3 does not say which wins.

**Recommendation:** the ceiling wins and the engine emits `CEILING_BELOW_PLAN_NEED`, surfacing both numbers so the requester can justify the difference. The ceiling is a guard rail against over-ordering, which is the initiative's purpose; silently exceeding it would defeat it. **This needs VZI confirmation** (see §9).

## 5. Design — module layout

Following the conventions the codebase already enforces: pure domain logic with no I/O and no wall-clock reads, config through `Settings` → `I13Config`, thin routes, and a persisted mart mirroring `consumption_attribution_mart.py`.

```
app/initiatives/i13/
  quantity_suggestion.py          NEW  pure calculation — no I/O, no datetime.now()
  quantity_suggestion_mart.py     NEW  persistence + refresh, mirrors W6.4's mart
  config.py                       EDIT + QuantitySuggestionConfig dataclass
app/models/
  i13_quantity_suggestion.py      NEW  QuantitySuggestion + Justification tables
app/schemas/
  i13_quantity.py                 NEW  request/response contracts
app/api/i13/
  quantity_suggestion.py          NEW  thin route
  routes.py                       EDIT mount the sub-router
app/core/config.py                EDIT + 4 settings
alembic/versions/                 NEW  one migration
tests/i13/
  test_quantity_suggestion.py     NEW  boundary tests
```

### Where the LLM does and does not belong

The Dev Plan lists W1.5 as a dependency. **The LLM must not produce the number.** The quantity is deterministic arithmetic and must be reproducible and auditable — the same reasoning that keeps stitching deterministic under D9.

The AI layer is used **only to phrase the reason** for the requester, from the structured reason code and the computed figures, via `get_llm()`. If the model is unavailable the engine still returns the number and a deterministic fallback sentence. This matches the existing rule that business logic never imports a provider SDK.

## 7. Configuration — four new settings

Per FRS §6 these are configuration, not code.

| Setting | Default | Note |
| --- | --- | --- |
| `I13_QTY_COVER_CEILING_MONTHS` | **none** | VZI open item |
| `I13_QTY_MINIMUM_HISTORY_COUNT` | **none** | VZI open item |
| `I13_QTY_LOOKBACK_MONTHS` | `12` | Recommend reusing `I13_CONSUMPTION_WINDOW_MONTHS` unless VZI wants divergence |
| `I13_QTY_SUGGESTION_ENABLED` | `false` | Master gate |

**Recommendation: ship no invented default for the ceiling or minimum history.** With them unset the engine returns `NO_SUGGESTION` with reason `NOT_CONFIGURED`. This matches how `I13_HOD_RECIPIENTS` already behaves — empty means routing reports Pending rather than inventing a recipient. A guessed ceiling would silently produce plausible-looking but unsanctioned purchase advice.

## 8. API surface

| Endpoint | Purpose |
| --- | --- |
| `POST /api/i13/quantity-suggestion` | Compute and persist a suggestion. Body: material, plant, requested quantity, plan window, optional session id |
| `GET /api/i13/quantity-suggestion/{id}` | Retrieve one |
| `GET /api/i13/quantity-suggestion` | List, filtered by material/plant/session, **with `limit`/`offset`** |
| `POST /api/i13/quantity-suggestion/{id}/justification` | Capture an override justification |
| `POST /api/i13/quantity-suggestion/{id}/acceptance` | Record accepted / not accepted (FRS §8) |

Pagination is mandatory on the list route — several existing I13 list endpoints lack it and return unbounded payloads; do not repeat that.

## 9. Open questions for VZI — blocking

The engine cannot be switched on until 1 and 2 are answered.

| # | Question | Impact |
| --- | --- | --- |
| 1 | **Cover ceiling, in months?** | No default exists; FRS §10 carries it as open |
| 2 | **Minimum history — how much, and measured how?** Count of consumption events, or months of history? | See the coverage table below — this single value determines how often the engine speaks at all |
| 3 | Look-back: reuse the existing 12-month window, or a separate one? | Recommend reuse |
| 4 | **When the plan window needs more than the ceiling allows, which wins?** | Recommend ceiling; needs confirmation |
| 5 | Rounding — to base UoM, pack size, or order multiple? | Affects every suggested figure |
| 6 | "Accepted" for savings — exact match, or within a tolerance? | Drives §8 benefit reporting |

### Why question 2 matters most

Measured against the current WATCH mart (7,184 positions):

| Minimum history | Positions that would receive a suggestion |
| --- | --- |
| Any consumption (> 0) | 3,086 — **43%** |
| ≥ 4 consumptions in 12M | 459 — **6.4%** |

Set at 4, the engine declines on roughly 94% of positions. That may well be correct — a suggestion on one data point is worse than no suggestion — but VZI should choose it knowing the coverage consequence.

## 10. Data risks affecting correctness

These do not block the build, but they bias the output and should be understood before anyone acts on a suggestion.

| # | Risk | Effect on W7.4 |
| --- | --- | --- |
| 1 | **MCHB not read; `BatchStockSet` returns HTTP 400.** Stock on hand is MARD-only, and 7,419 MCHB rows belong to OAR material-plants | **Stock understated → the engine suggests buying more than needed.** The most direct correctness risk in this package |
| 2 | **EKET not read.** Open-PO netting approximates from EKPO − EKBE | FRS §7 names EKET for exactly this. Approximation is reasonable but should be stated |
| 3 | **Movement history is ~12.5 months.** AMC over a 12-month look-back sits right at the edge of available data | Materials whose consumption predates the window read as AMC = 0 → no suggestion. Safe, but suppresses coverage |
| 4 | **I12 duplicate stock codes** — FRS §8 names this an entry criterion | Duplicates split consumption history and understate AMC, distorting every suggestion for the affected codes |

Risk 1 is worth escalating alongside the build: a quantity engine whose stock figure is systematically low will systematically over-order, which is the opposite of the initiative's purpose.

## 11. Test plan

Mirroring the boundary discipline W3.5 already follows (365/366/730/731):

**Gate**
- `AMC = 0` → `NO_SUGGESTION` / `INSUFFICIENT_HISTORY`
- `HIST` at `MIN_HIST − 1`, `MIN_HIST`, `MIN_HIST + 1`
- Config unset → `NO_SUGGESTION` / `NOT_CONFIGURED`

**Ceiling**
- `Q_req` at `ceiling_qty − 1`, exactly `ceiling_qty`, `ceiling_qty + 1`
- `SOH + OPO` already above the ceiling → `ceiling_qty = 0`

**Plan need**
- `Q_req` at `net_need − 1`, exactly `net_need`, `net_need + 1`
- `SOH + OPO ≥ plan_need` → `net_need = 0`

**Conflict**
- `net_need > ceiling_qty` → `CEILING_BELOW_PLAN_NEED`, both figures present

**Discipline**
- Decimal throughout, no float
- No `datetime.now()` inside pure functions — `as_of` passed in
- LLM unavailable → number unchanged, deterministic fallback reason
- Round-trip through the API preserves the config snapshot

## 12. Definition of done

- [ ] Suggestion computed deterministically from W6.3 inputs for a real material/plant
- [ ] Ceiling and shortfall nudges both demonstrated on real data, with reasons
- [ ] Engine declines with an explicit reason where history is below minimum, and never guesses
- [ ] Cover ceiling, minimum history and look-back are configuration; unset config disables the engine rather than defaulting
- [ ] `QuantitySuggestion` and `Justification` persisted, with the config snapshot
- [ ] Acceptance recordable, so FRS §8 savings attribution is possible
- [ ] **`suggested_quantity` flows into W6.6's `QuantityDecisionRecord` and raises a quantity-override exception** — the package is not done until that idle path fires
- [ ] Boundary tests pass; list endpoint paginated
- [ ] LLM used only for reason phrasing, never for the number
